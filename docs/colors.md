# Preserving colors in child tools

Some tools stop generating colored output when their output is connected to a pipe rather than a terminal (TTY).
`--print-label` uses pipes to prefix child stdout and stderr, and `--aggregate-output` buffers child stdout through a pipe.
Aggregation alone does not buffer stderr, but a tool may use stdout's terminal capabilities to decide whether to color both streams.
The Node API options `printLabel` and `aggregateOutput` have the same behavior.

`npm-run-all2` preserves ANSI color sequences emitted by child tools; it does not strip colors, automatically set `FORCE_COLOR`, inject tool-specific flags, or allocate pseudo-terminals.
The `--color-mode` option controls task label colors, not colors generated by child tools.

## Start with `FORCE_COLOR=1`

Many tools support the `FORCE_COLOR` environment variable, which requests colors even when output is piped.
Set it before launching `npm-run-all`, `run-p`, or `run-s` so child tools inherit it.
For example, with existing `lint:*` scripts:

```sh
# macOS / Linux / other POSIX shells
FORCE_COLOR=1 run-p --aggregate-output 'lint:*'
```


Check for conflicting settings such as `NO_COLOR`, `NODE_DISABLE_COLORS`, and a tool's `--no-color` option.
Their precedence varies between tools, so `FORCE_COLOR=1` is not a universal override.
Likewise, do not rely on `FORCE_COLOR=0` as a universal way to disable colors: some libraries treat any nonempty value, or even the variable's presence, as an enable request.

## Tool-specific controls and quirks

Put tool-specific flags in the leaf script that invokes the tool, not on `npm-run-all` itself.
For example:

```json
{
  "scripts": {
    "lint:types": "tsc --noEmit --pretty true",
    "lint:js": "eslint --color .",
    "lint": "run-p --aggregate-output lint:*"
  }
}
```

The following inventory is based on upstream documentation and source inspection, not an automated compatibility matrix.
Behavior can change between versions and can differ for custom formatters, reporters, and plugins.

| Tool | How to request colors through a pipe | Quirks |
| --- | --- | --- |
| [TypeScript `tsc`][typescript-pretty] | `tsc --pretty true`, or `"pretty": true` in `compilerOptions`. | In [TypeScript 5.9.3][typescript-source], automatic pretty diagnostics depend on stdout being a TTY and `NO_COLOR` not being set; explicit `pretty` overrides that default. `FORCE_COLOR` is not the diagnostic override. Pretty output also adds source context, and compiler help has separate color detection. |
| [Vitest][vitest-source] | `FORCE_COLOR=1 vitest run` or `vitest run --color`. | Vitest 4.0.0's normal reporters use [tinyrainbow 3.0.3][tinyrainbow-source], which recognizes these overrides. `NO_COLOR` or `--no-color` disables its colors even with a force request. TTY-dependent live summaries and keyboard interaction are separate from ANSI colors; use a static reporter such as `--reporter=verbose` when more test detail is needed. |
| [es-check][es-check-source] | No working force-color override for ordinary piped stdout was found in the built-in logger in 9.8.1 / 9.9.0. | These versions reject non-TTY stdout before considering `FORCE_COLOR`, including for messages later written to stderr. `--noColor` / `--no-color` can disable colors but cannot force them on. This is version-specific: [7.2.1][es-check-older] used `supports-color`, which supports `FORCE_COLOR=1` through a pipe. |
| [ESLint][eslint-color] | `eslint --color`, or `FORCE_COLOR=1` with the default formatter. | `--color` explicitly overrides terminal detection. Custom formatters may use different detection rules. |
| [Stylelint][stylelint-color] | `stylelint --color`, or `FORCE_COLOR=1`. | Color flags control formatted results; custom formatters may behave differently. |
| [Vite][vite-source] | `FORCE_COLOR=1`. | Its built-in logger uses [picocolors][picocolors-source], where nonempty `NO_COLOR` takes precedence over `FORCE_COLOR`. Do not assume the Vite CLI accepts `--color` merely because the color library recognizes that argument. |
| [Rollup][rollup-source] | The checked upstream color helper enables colors unless `FORCE_COLOR=0` or nonempty `NO_COLOR` disables them. | It explicitly enables its palette without relying on TTY detection, so it may already color piped output. CLI diagnostics use stderr rather than the bundle output on stdout. |
| [Prettier][prettier-source] | `prettier --color`, or `FORCE_COLOR=1`, for diagnostic logging. | Nonempty `NO_COLOR` or `--no-color` takes precedence in the checked logger. This does not syntax-highlight formatted source written to stdout or files. |

For a tool without a working override, prefer reporting its color-detection limitation upstream rather than assuming every tool needs a terminal.
Forcing colors does not restore terminal interactivity, progress redraws, or terminal-width-dependent layouts.
When reporting a missing-color issue, include the tool and version, formatter or reporter, relevant environment variables, the affected stream, and whether `--print-label`, `--aggregate-output`, or both are enabled.
